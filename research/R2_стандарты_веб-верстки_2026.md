# R2. Стандарты веб-вёрстки и фронтенда 2026 — проверка стека iPrint

Дата исследования: 17.11.2026. Планируемый стек: Astro (статический вывод) + Cloudflare + GitHub, форма заявки → Telegram-бот, автоматическое сжатие фото, 80–90% мобильного трафика, только украинский язык, светлая/тёмная тема.

> **Главные поправки к стеку (кратко):**
> 1. **Cloudflare Pages → Cloudflare Workers со статическими ассетами.** На главной странице документации Pages сейчас висит баннер: «Start new projects with Workers». Pages работает и поддерживается, но новые функции идут в Workers.
> 2. **Для Workers домен должен обслуживаться DNS Cloudflare** (смена NS у регистратора). Pages умел подключать домен без переноса NS, Workers — нет.
> 3. **Astro сейчас на 7-й версии** (7.0 вышла 22.06.2026, на 13.11 последняя — 7.4.12). Старые туториалы под Astro 4/5 частично устарели.
> 4. Всё остальное (статический Astro, форма через серверный код Cloudflare, Turnstile, AVIF/WebP) подтверждается как актуальная практика.

## 1. Core Web Vitals и Lighthouse

- Три метрики не менялись с марта 2024 (тогда INP заменил FID). Пороги «хорошо», по 75-му перцентилю реальных визитов, отдельно для мобильных и десктопа:
  - **LCP** (загрузка главного элемента) ≤ **2,5 с** (плохо > 4 с);
  - **INP** (отклик на нажатия) ≤ **200 мс** (плохо > 500 мс);
  - **CLS** (сдвиги вёрстки) ≤ **0,1** (плохо > 0,25).
- В блогах 2026 года встречаются утверждения, что Google «ужесточил INP до 150 мс» (март 2026). **В официальных источниках (web.dev, Search Central) подтверждения не найдено** — считать слухом. По правилам Google стабильные метрики меняются не чаще раза в год и с публичным анонсом.
- Lighthouse — лабораторный тест (одна загрузка, эмуляция слабого телефона). Веса Lighthouse 10+ (действуют и в более новых версиях, насколько удалось проверить): TBT 30%, LCP 25%, CLS 25%, FCP 10%, Speed Index 10%. Цвета: 0–49 красный, 50–89 оранжевый, 90–100 зелёный. INP в лаборатории не измеряется — его заменяет TBT.
- У маленького сайта долго не будет полевых данных CrUX в PageSpeed Insights (мало трафика) — ориентироваться придётся на Lighthouse.

**→ Что это значит для проекта.** Цели для статического сайта: Lighthouse Mobile Performance ≥ 90 (реально 95–100), Accessibility/Best Practices/SEO = 100; LCP < 2,0 с на эмуляции 4G; CLS < 0,05 (у всех картинок заданы width/height); JS на странице минимальный (переключатель темы, меню, форма) → INP без проблем. Главный риск для LCP — тяжёлое фото в первом экране и шрифты.

## 2. Доступность (WCAG 2.2 AA)

- **WCAG 2.2** (W3C Recommendation, октябрь 2023) — действующий стандарт. **WCAG 3.0** — по-прежнему только Working Draft (9-й черновик от 03.03.2026), даты финала нет; реалистично не раньше 2027–2028. Ориентироваться на 2.2 AA.
- Ключевые требования для нашего сайта:
  - **Контраст** (1.4.3): текст ≥ **4,5:1**, крупный текст (≥ 24 px или ≥ 18,66 px жирный) ≥ **3:1**; иконки, рамки полей, состояния фокуса ≥ **3:1** (1.4.11). Проверять **в обеих темах**.
  - **Размер цели нажатия** (2.5.8, AA, новое в 2.2): минимум **24×24 CSS px** (или достаточный отступ). Рекомендация AAA (2.5.5) и Apple HIG — **44×44 px**; Material — 48×48 dp. Для мобильного сайта берём 44–48 px.
  - **Видимый фокус** (2.4.7) + **фокус не перекрыт** липкой шапкой (2.4.11, новое в 2.2) → `scroll-padding-top` под высоту шапки.
  - **Reflow** (1.4.10): без горизонтальной прокрутки на ширине **320 px**.
  - **Движение**: уважать `prefers-reduced-motion` (отключать параллакс, автопрокрутку, длинные анимации).
  - Формы: видимые подписи (`<label>`), понятные ошибки текстом, без ограничения по времени; 3.3.7 «не просить повторно вводить одно и то же».
  - `lang="uk"` на `<html>`, alt-тексты у фото работ, логичная иерархия заголовков.
- **European Accessibility Act** (применяется с 28.06.2025): касается услуг, в т.ч. e-commerce, оказываемых **потребителям в ЕС**. Микропредприятия (< 10 сотрудников и оборот/баланс ≤ 2 млн €) по услугам освобождены. Сайт-визитка украинской типографии на украинском без онлайн-продаж в ЕС — **прямо под EAA, скорее всего, не попадает** (не юридическая консультация).
- Украина: действует **ДСТУ EN 301 549:2022** (с 15.06.2022, идентичен европейскому). Законопроект «Про цифрову доступність» предполагает обязанности для ряда частных сфер, микробизнес, по обзорам, освобождён; ухвален ли он — не подтверждено.

**→ Что это значит.** Делаем WCAG 2.2 AA как стандарт качества (это ещё и SEO, и удобство на телефоне), а не из-за юридической обязанности. Проверка: Lighthouse Accessibility + axe (можно встроить в Playwright-тесты через `@axe-core/playwright`).

## 3. Современный CSS: что можно использовать в 2026

Baseline = работает во всех основных движках (Chrome/Edge, Firefox, Safari macOS+iOS). «Widely available» = 30 месяцев после этого.

| Возможность | Статус | Минимальный iOS Safari |
|---|---|---|
| `clamp()` (плавная типографика) | Widely | 13.4 |
| Cascade layers `@layer` | Widely | 15.4 |
| `:has()` | Widely с 19.06.2026 | 15.4 |
| Container queries (`@container`) | Widely с 14.08.2025 | 16.0 |
| CSS nesting (современный синтаксис) | Widely с 11.06.2026 | 17.2 |
| `oklch()` / `oklab()` | Widely (Baseline 2023)* | 15.4* |
| `light-dark()` + `color-scheme` | Widely с ~13.11.2026 | 17.5 |
| `@property` | Newly (Widely ожидается 09.01.2027) | 16.4 |
| View Transitions внутри страницы | Newly (с окт. 2025, Firefox 144) | 18.0* |
| View Transitions **между страницами** (`@view-transition`) | **Limited** — нет в Firefox | 18.2 |

\* — версия по памяти/вторичным источникам, сверить на caniuse перед использованием.

**→ Что это значит.** Пишем на нативном CSS (nesting, layers, container queries, `:has()`, `clamp()`, oklch) — Sass не нужен. Важный нюанс: CSS nesting требует iOS 17.2+, а `light-dark()` — iOS 17.5+. Устройства на iOS 16 (iPhone 8/X) получат сломанные стили, если не подстраховаться. Варианты: (а) принять порог iOS 17.5+ (доля старше — единицы процентов, сверить по StatCounter/Cloudflare Web Analytics после запуска); (б) Astro/Vite через Lightning CSS может «разворачивать» nesting в плоский CSS по `browserslist` — проверить при настройке. Переходы между страницами (`@view-transition`) — только как украшение, в Firefox просто не будет анимации.

## 4. Переключение темы: лучшая практика

1. **По умолчанию — системная тема** (`prefers-color-scheme`). Удобно делать 3 состояния: «Системна / Світла / Темна» (или 2-кнопочный переключатель, но с первым визитом по системе).
2. В `<head>`: `<meta name="color-scheme" content="light dark">` и два `<meta name="theme-color" media="(prefers-color-scheme: …)">` — цвет адресной строки Safari/Chrome на телефоне.
3. **Без вспышки неправильной темы**: маленький **inline-скрипт в `<head>` до стилей/контента** (в Astro — `<script is:inline>`), читает `localStorage` (в `try/catch` — в приватном режиме Safari может бросать ошибку) и ставит `data-theme` на `<html>` до первой отрисовки.
4. CSS: `:root { color-scheme: light dark; }`, `:root[data-theme="light"] { color-scheme: light; }`, `:root[data-theme="dark"] { color-scheme: dark; }`, цвета через `light-dark(светлый, тёмный)` в CSS-переменных. Тогда `light-dark()` автоматически следует выбору пользователя, а системные элементы (скроллбары, поля форм) тоже перекрашиваются.
5. Кнопка — настоящий `<button>` с `aria-label` / `aria-pressed`, размер ≥ 44 px, контраст в обеих темах.
6. Если используется Astro `<ClientRouter />` — повторно применять тему на событии `astro:after-swap`. Для сайта-визитки ClientRouter не обязателен.
7. Фото работ не инвертировать; логотип — отдельный вариант для тёмного фона (`<picture>` с `media="(prefers-color-scheme: dark)"` не учитывает ручной выбор — лучше SVG с `currentColor` или переключение через CSS).

**→ Что это значит.** Тема реализуема без библиотек, ~20 строк JS. Если включается CSP (п. 10) — inline-скрипт нужно разрешить через hash.

## 5. Astro

- **Текущая мажорная версия — Astro 7** (7.0 — 22.06.2026; на GitHub последняя `astro@7.4.12` от 13.11). Главное в 7: компилятор переписан на Rust (строже — незакрытые теги дают ошибку), Vite 8, новый Markdown-процессор Sätteri по умолчанию, `compressHTML: 'jsx'` (пробелы между inline-элементами могут пропадать — ставить `{' '}`).
- **Node.js**: для Astro 6 — **≥ 22.12.0**; для Astro 7 в гайде обновления требование не указано явно — использовать актуальный LTS (22 или 24) и проверить `engines` в package.json при установке.
- **Изображения** (`astro:assets`, сервис sharp по умолчанию):
  - исходники класть в `src/` (из `public/` картинки **не** обрабатываются);
  - `<Picture formats={['avif','webp']} />` → `<picture>` с AVIF, WebP и запасным форматом;
  - адаптивность: `layout="constrained" | "full-width" | "fixed"` (или глобально `image.layout`) → автоматически `srcset` и `sizes`; включить `image.responsiveStyles: true`;
  - `priority` (с 5.10) для фото первого экрана → `loading="eager"`, `decoding="sync"`, `fetchpriority="high"`; все остальные — lazy по умолчанию;
  - `width`/`height` проставляются автоматически → нет CLS;
  - `quality` — пресеты `low/mid/high/max` или 0–100.
  - **Для статического вывода сжатие идёт при сборке**, на сервере Cloudflare ничего не нужно. (Ограничение «на Cloudflare нет sharp» касается только SSR-режима с адаптером.)
- **Шрифты**: встроенный **Fonts API** (появился в Astro 6, конфиг `fonts` + компонент `<Font />`). Скачивает и **самохостит** шрифт с Google/Fontsource/Bunny, генерирует оптимизированный fallback (меньше CLS), умеет preload. Manrope (OFL, вариативный 200–800) на Google Fonts **имеет subset `cyrillic`** (проверено — также `cyrillic-ext`, `latin`, `latin-ext`) → `subsets: ['cyrillic','latin']`. Украинские ґ є і ї входят в базовый `cyrillic`. Google по умолчанию отдаёт `font-display: swap`.
- **Content collections**: схемы на Zod 4 (импорт из `astro/zod`), удобно для услуг/портфолио/отзывов в Markdown/JSON.
- **Sitemap**: `@astrojs/sitemap` + обязательно задать `site` в конфиге.
- **CSP**: `security.csp` (с 6.0) — Astro сам добавляет `<meta http-equiv="content-security-policy">` с хешами своих скриптов/стилей; не работает в `dev`, несовместим с `<ClientRouter />`.

**→ Что это значит.** Astro подтверждён как отличный выбор. Брать Astro 7, без UI-фреймворков (React/Vue не нужны). Конвейер «фото 3–5 МБ → AVIF/WebP нескольких ширин» встроен — отдельный инструмент не нужен. Минус: исходники в git тяжёлые (100 фото × 4 МБ = 400 МБ в репозитории) → до коммита уменьшать оригиналы до ~2560 px по длинной стороне (скриптом на sharp), это даст 0,5–1 МБ на фото.

## 6. Cloudflare: Pages или Workers

- **Официальная позиция 2026: «Start new projects with Workers»** (баннер на docs Pages: «Workers supports most Pages use cases and offers a broader feature set»). Pages не закрыт, но это путь «для существующих проектов».
- **Workers со статическими ассетами — что есть:**
  - запросы к статике **бесплатны и без лимита**; код Worker вызывается только для не-статических путей (например `/api/lead`);
  - `_redirects` и `_headers` поддерживаются (файлы в папке сборки, т.е. в `public/` у Astro);
  - `not_found_handling: "404-page"` — отдавать `404.html`;
  - Workers Builds из GitHub: сборка при каждом push; **ветки ≠ production → Preview URL** (отдельная ссылка на каждую ветку); версии получают свои URL вида `<id>-<имя>.<subdomain>.workers.dev`; можно закрыть превью через Cloudflare Access;
  - статический Astro деплоится **без адаптера**: `wrangler.jsonc` с `assets.directory: "./dist"`.
- **Лимиты Free:** 100 000 запросов к Worker/сутки (статика не в счёт), 10 мс CPU на запрос (для пересылки формы в Telegram хватает — ожидание сети не считается CPU), 50 subrequests, **20 000 файлов** и **25 MiB на файл** в версии; Builds — **3 000 минут/мес, 1 одновременная сборка, таймаут 20 мин**, 2 vCPU / 8 ГБ.
- **Отличия, важные нам:** Workers **требует, чтобы домен был на DNS Cloudflare** (Pages умел без этого); Workers сначала отдаёт статику, потом код (для `/api/*` использовать `run_worker_first: ["/api/*"]` или просто путь, которого нет в статике).

**→ Что это значит.** **Поправка к стеку: деплой на Workers static assets, не Pages.** Схема: Astro собирает `dist/` → один `wrangler.jsonc` с `assets` + маленький `main`-скрипт (≈50 строк) только для `POST /api/lead`. Адаптер `@astrojs/cloudflare` не нужен (вариант с адаптером и `prerender` тоже возможен, но сложнее). Домен iPrint перенести на NS Cloudflare. Сборка 100+ фото в AVIF может занимать минуты — укладываемся в 20 мин, но AVIF-кодирование медленное: следить; при необходимости кешировать или собирать в GitHub Actions.

## 7. Форма → Telegram-бот

- **Токен бота — только на сервере**: секрет Worker (`wrangler secret put TELEGRAM_BOT_TOKEN`, `TELEGRAM_CHAT_ID`), **никогда** в клиентском JS/репозитории (токен даёт полный контроль над ботом). Секреты отдельно для превью и прода.
- Поток: форма (обычный HTML `<form>`, работает и без JS) → `POST /api/lead` (Worker) → проверки → `sendMessage` (`https://api.telegram.org/bot<TOKEN>/sendMessage`) → ответ «Дякуємо» / редирект на страницу «дякуємо».
- **Антиспам, слоями:**
  1. **Cloudflare Turnstile** (бесплатная «невидимая капча»): токен проверяется **на сервере** через `siteverify` с секретным ключом; токен живёт **300 с** и одноразовый; проверять `success`, `hostname`, `action`. Без серверной проверки Turnstile бесполезен.
  2. **Honeypot**-поле (скрытое, бот заполняет — отбрасываем) + минимальное время заполнения.
  3. Валидация длины/формата на сервере (телефон, имя, текст ≤ N символов), экранирование `<`, `>`, `&` при `parse_mode: HTML`.
  4. Опционально — Rate Limiting binding Cloudflare.
- **Ограничения Telegram** (по документации Bot API; текущая версия 10.4 от 09.11.2026): текст сообщения ≤ 4096 символов; `sendDocument` — до 50 МБ, `sendPhoto` — до 10 МБ; не более ~1 сообщения/с в один чат (точные лимиты сверить в FAQ ботов).
- **Загрузка файлов (макеты, логотипы):** проще всего — Worker принимает `multipart/form-data` и пересылает файл через `sendDocument` (лимит запроса Free-плана 100 МБ, реальный — 50 МБ Telegram). Ограничить: 1–3 файла, ≤ 20 МБ, типы PDF/AI/SVG/PNG/JPG/CDR. На мобильном интернете большие файлы — плохой UX; альтернатива — поле «ссылка на Google Drive».
- **Резерв:** если Telegram недоступен — запасной канал (e-mail через сервис или запись в Cloudflare D1/KV), иначе заявка потеряется. Показывать пользователю телефон/Viber/Telegram-ссылку как альтернативу.
- **Персональные данные (Украина):** действует Закон № 2297-VI «Про захист персональних даних»; новый законопроект № 8153 (в духе GDPR) принят в первом чтении 20.11.2024, окончательное принятие **не подтверждено**. Минимум: собирать только нужное (имя, телефон, описание), чекбокс/текст согласия рядом с кнопкой, страница «Політика конфіденційності» (кто оператор, цель, срок хранения, право удалить; что данные пересылаются в Telegram — сервис за пределами Украины). Не юридическая консультация.

**→ Что это значит.** План подтверждён; обязательные элементы: серверный Worker с секретами, Turnstile + honeypot, страница политики, резервный канал.

## 8. Кроссбраузерное и мобильное тестирование

- **Playwright** (последняя — 1.65; Chromium 158, Firefox 159, WebKit 27.2) запускает три движка на Windows и Linux. WebKit в Playwright — **ближайшее к Safari, но не iOS Safari**: другая сборка, нет интерфейса Safari (плавающая адресная строка, нижняя панель), иначе шрифты/рендер, нет реального поведения клавиатуры, `100vh`/`dvh`, safe-area «чёлки», автозума полей.
- Эмуляция устройств: `devices['iPhone 13']` и т.п. задаёт viewport, userAgent, deviceScaleFactor, `isMobile`, `hasTouch`; плюс `colorScheme: 'dark'`, `reducedMotion: 'reduce'`, `locale: 'uk-UA'`, `timezoneId: 'Europe/Kyiv'` — удобно гонять обе темы.
- На iPhone **все браузеры (и Chrome) работают на WebKit** — значит, тестировать Safari/WebKit критично.
- **Реальные устройства, дёшево:** (1) собственный iPhone + Android владельца по Preview-ссылке Cloudflare — обязательный ручной чек перед релизом; (2) облачные фермы BrowserStack / LambdaTest — бесплатные пробные минуты, достаточно для разовой проверки; (3) отладка Safari Web Inspector требует Mac.
- iOS-ловушки: шрифт в полях ≥ **16 px** (иначе зум при фокусе), `100dvh`/`svh` вместо `100vh`, `env(safe-area-inset-*)`, `<input type="tel" inputmode="tel" autocomplete="tel">`.
- **Матрица ширин (CSS px)**. StatCounter, Украина, мобильные, июнь 2026: 375×812 ≈ 33%, 414×896 ≈ 14%, 393×873 ≈ 7%, 360×800 ≈ 4%.
  - 320 (минимум WCAG reflow), **360** (бюджетные Android), **375** (самая массовая в UA), **390/393** (iPhone 12–16, Pixel), **412/414** (крупные Android/старые iPhone Plus), **430/440** (iPhone Pro Max);
  - планшеты 768, 1024; десктоп 1280, 1440, 1920.
  - Минимальный автоматический набор: 360, 375, 393, 414, 768, 1280, 1920 × (Chromium, WebKit, Firefox) × (светлая, тёмная).

**→ Что это значит.** Playwright подтверждён как основной инструмент (скриншоты + axe + проверка отправки формы на превью); финальная проверка — живой iPhone.

## 9. Изображения

- **AVIF**: поддержка во всех основных браузерах; в Safari — с 16.0 (iOS 16, 2022), на iOS ≤ 15 нет → нужен WebP/JPEG fallback, что `<Picture>` делает сам. **WebP** — универсальный запасной вариант.
- **`fetchpriority="high"`** — Baseline с 29.10.2024 (Chrome 102, Safari 17.2, Firefox 132). Ставить **только на LCP-картинку** (hero) и **никогда** не делать её lazy.
- `loading="lazy"` — для всего ниже первого экрана; `decoding="async"`.
- Всегда `width`/`height` или `aspect-ratio` → CLS ≈ 0.
- `sizes` должен соответствовать вёрстке (для мобильного первого экрана обычно `100vw`) — иначе телефон грузит лишнее.
- Ориентиры веса: hero на мобильном ≤ 100–150 КБ (AVIF), карточки портфолио 30–80 КБ; ширины 400/800/1200/1600(/2400 для full-width).

**→ Что это значит.** Всё это закрывает `<Picture formats={['avif','webp']} layout=… priority />` из Astro — достаточно соблюдать правила при вёрстке.

## 10. Безопасность статического сайта

- **HTTPS**: в Cloudflare включить «Always Use HTTPS» и минимум TLS 1.2. **HSTS** включать в панели (SSL/TLS → Edge Certificates) или заголовком `Strict-Transport-Security: max-age=31536000; includeSubDomains` — **сначала с малым max-age**, `preload` только когда уверены во всех поддоменах (откат долгий).
- Заголовки через файл `public/_headers`: `X-Content-Type-Options: nosniff`, `Referrer-Policy: strict-origin-when-cross-origin`, `Permissions-Policy: camera=(), microphone=(), geolocation=()`, `X-Frame-Options: DENY` (или `frame-ancestors 'none'` в CSP).
- **CSP**: базово `default-src 'self'; img-src 'self' data:; script-src 'self' https://challenges.cloudflare.com; frame-src https://challenges.cloudflare.com; connect-src 'self'` (Turnstile требует свои домены). Inline-скрипт темы — разрешить через **hash** (или встроенный `security.csp` Astro, который хеширует сам — проверить, что inline-скрипт темы попадает в хеши). Сначала включать `Content-Security-Policy-Report-Only`.
- Секреты только в Worker secrets; в репозитории — `.dev.vars` в `.gitignore`.
- Встроенная карта Google/YouTube требует расширять CSP; лучше статичная картинка карты со ссылкой.

**→ Что это значит.** Безопасность на статике простая: `_headers` + HTTPS/HSTS + секреты на сервере. Проверка — securityheaders.com и Mozilla Observatory после запуска.
